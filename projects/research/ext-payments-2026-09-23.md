# Chrome extension payments: Stripe Managed Payments vs ExtensionPay vs DIY serverless
Research date: 2026-09-23

## 1. Is ExtensionPay compatible with Stripe Managed Payments?

**Short answer: almost certainly NOT, or at best undocumented/risky.**

- ExtensionPay (extensionpay.com / the ExtPay.js library) works by having the developer "connect their own Stripe account" to ExtensionPay from the ExtensionPay dashboard. Funds are paid **directly into the developer's own Stripe account**, not into ExtensionPay's account — ExtensionPay's own copy says "Your data is stored in Stripe so you can migrate away from ExtensionPay whenever you like." ([extensionpay.com](https://extensionpay.com/articles/add-stripe-payments-to-chrome-extensions))
- Neither ExtensionPay's public articles nor the open-source ExtPay.js docs on GitHub state explicitly whether the connection mechanism is Stripe Connect (Standard/Express) OAuth or something else — this is genuinely undocumented in public materials I could fetch. ([GitHub Glench/ExtPay](https://github.com/Glench/ExtPay/blob/main/docs/how_subscriptions_work.md))
- However, the pattern described ("link your Stripe account to a third-party platform; the platform's dashboard/API then creates products, checkout sessions, and reads payment status on the developer's behalf; funds settle to the developer's own account") is exactly the Stripe Connect integration pattern. A directly-competing service, BillingExtensions, describes its equivalent flow explicitly as "Link an existing or new Stripe account via Stripe Connect," which is functionally the same model. This strongly suggests ExtensionPay also operates as a Connect platform with the developer's account as a connected account.
- This matters because Stripe's own Managed Payments eligibility docs state explicitly: **"Managed Payments supports direct integrations only. It doesn't support: Connect platforms, Express accounts, Accounts controlled by a platform."** ([docs.stripe.com/payments/managed-payments/eligibility](https://docs.stripe.com/payments/managed-payments/eligibility)) The comparison table on the Managed Payments overview page likewise lists "Support for platforms" as "Unsupported" for Managed Payments (only available via Connect). ([docs.stripe.com/payments/managed-payments](https://docs.stripe.com/payments/managed-payments))
- **Conclusion:** if the owner's Stripe account is connected to ExtensionPay as a Connect account (Standard or Express), Managed Payments cannot be enabled on that account for those transactions — the two are mutually exclusive per Stripe's own eligibility rules. Even if ExtensionPay's Connect flow uses "Standard" accounts (where the developer nominally remains merchant of record for tax purposes already, so VAT is NOT handled by Stripe on ExtensionPay transactions regardless), Stripe still classifies the account as platform-controlled and excludes it from Managed Payments. **Net effect: paying ExtensionPay's ~5% fee does not buy you Stripe-as-merchant-of-record VAT handling; you would still be your own merchant of record for global VAT on ExtensionPay-processed sales**, unless ExtensionPay itself operates as a merchant of record (no evidence of this in their public materials — they describe themselves purely as a payment-facilitation/backend-replacement tool, not a MoR/tax entity).
- **Recommendation:** treat ExtensionPay + Managed Payments as incompatible. If Managed Payments (i.e., Stripe as VAT/GST merchant of record) is a hard requirement, do not route through ExtensionpPay's Connect-style integration — use a direct Stripe integration instead (see #4).
- ExtensionPay fees: ExtensionPay charges "a small fee whenever a user pays" — third-party sources cite **5% flat** per transaction, charged **on top of** Stripe's own standard processing fee (2.9% + 30¢), with lower rates for high volume. ([extensionpay.com](https://extensionpay.com/), [dev.to comparison](https://dev.to/ktg0215/monetizing-chrome-extensions-with-freemium-real-numbers-from-7-paid-extensions-5cj))

## 2. What is Stripe Managed Payments (2025-2026)?

- Managed Payments is Stripe's merchant-of-record (MoR) product: **Stripe itself becomes the seller of record** for the transaction, taking on responsibility for indirect tax (VAT/GST/sales tax) compliance, fraud prevention, dispute/chargeback handling, and transaction-level customer support (via Link). ([stripe.com/managed-payments](https://stripe.com/managed-payments), [docs.stripe.com/payments/managed-payments](https://docs.stripe.com/payments/managed-payments))
- Timeline: announced/previewed April 2025; by 2026 it is live in the API — in April 2026 Stripe added a `managed_payments` parameter to Checkout Sessions and Payment Links (per Stripe's changelog), and it's now documented as a shipped product rather than a beta. Programmatic Payment Links access requires API version `2026-02-25.preview` or later per some integration reports — confirm current pinned version at build time. ([docs.stripe.com/changelog](https://docs.stripe.com/changelog/clover/2026-02-25/managed-payments))
- **How to enable it:** per Stripe's own docs, it can be turned on "with just a few clicks" in the Dashboard, or via a parameter on the Checkout Session / Payment Link creation call (`managed_payments`). Both the Dashboard payment-link creation flow and the API path require every product in the transaction to carry an **eligible tax code**.
- **Supported integrations:** Stripe **Checkout** (hosted page) and **Payment Links** — both explicitly supported. **Yes, a Payment Link can be used with Managed Payments** — Stripe's docs have a dedicated guide "Create payment links: Create payment links with Managed Payments enabled to start collecting payments for digital products." Subscriptions are supported via Stripe **Billing** on top of Checkout or Payment Links (but a subscription **cannot** be created outside of Checkout/Payment Links under Managed Payments — e.g., not via raw Subscriptions API directly). Mobile app payments are also supported (separate guide). **Not supported:** Stripe Elements / embeddable components, "advanced integrations," raw invoice-item attachment on Customer objects, one-off invoices outside a billing period, and (critically) **Stripe Connect** platform/marketplace integrations, Express accounts, or any account controlled by a platform.
- **Fees:** Managed Payments adds a flat **3.5%** on top of standard Stripe processing fees, covering tax, fraud, disputes, and Link-based support — no setup fee or monthly minimum. (One third-party competitor-analysis source claims an effective blended 7–9%, likely bundling in base card-processing fees; treat 3.5% as the incremental MoR fee on top of normal ~2.9%+30¢, i.e. roughly 6-7% all-in for card payments.) ([docs.stripe.com/payments/managed-payments](https://docs.stripe.com/payments/managed-payments))
- **Eligibility/restrictions** (from `docs.stripe.com/payments/managed-payments/eligibility`):
  - **Business type:** direct integrations only. Excludes Connect platforms, Express accounts, platform-controlled accounts.
  - **Business location:** must be based in one of a defined list of countries — includes US, Canada, UK, most of EU/EEA, Switzerland, Norway, Australia, Hong Kong, Japan, Singapore. (Full list in doc.)
  - **Product eligibility:** digital products only — software, video games, digital media (e-books, audiobooks, video/audio, images), online courses, and "electronically supplied" web/business services (e.g., hosting). Must be sold **directly to the end customer** (not through a marketplace/platform), fully automated (no material human involvement — rules out things like live 1:1 coaching), and the seller must hold full distribution rights.
  - **Every product needs an eligible tax code** (see list below) or the Checkout Session / Payment Link creation call fails with a 400 error ("the product tax code is missing"). This applies even to inline `price_data` (no Product object to inherit from), so the tax code must be set explicitly.
  - **Customer countries:** 195+ countries supported, with a short restricted list (China, Russia, Iran, North Korea, Cuba, Syria, Kosovo, Ascension Island, Tristan da Cunha).
  - **Ongoing requirements:** low dispute rate, no prior risk flags, Stripe can issue refunds within 60 days to preempt chargebacks, and Stripe enforces regional consumer-protection rules (e.g. cooling-off periods).
- **Relevant tax codes for a Chrome extension** (from Stripe's eligible list):
  - `txcd_10103000` — SaaS, personal use (recommended if premium features are delivered via your backend/cloud APIs and billed as a subscription to consumers)
  - `txcd_10103001` — SaaS, business use (if targeting business buyers)
  - `txcd_10202000` / `txcd_10202001` — Downloadable software, personal use (if better modeled as "software," non-recreational vs recreational split at `txcd_10202001`/`10202000`)
  - `txcd_10000000` — General "Electronically Supplied Services" fallback if none of the more specific categories fit well
  - **AI-specific codes exist** (`txcd_10105001`-`10105004`, AIaaS personal/business, cloud-only or hybrid cloud+downloaded) if the extension is specifically an AI tool (LLM wrapper, image generator, etc.) — likely the most accurate category if the "premium" features are AI-powered.

## 3. Cheapest robust ways to verify payment with no always-on server

| Option | Accounts needed | Cost | Effort | CWS policy notes |
|---|---|---|---|---|
| **(a) Edge function (Cloudflare Workers / Deno Deploy / Vercel Functions) holding a restricted Stripe key** | Stripe account + Cloudflare (or Deno Deploy/Vercel) account; optionally a KV/D1/SQL store to cache purchase state | Free tier: Cloudflare Workers free plan (100k req/day), D1 free tier (5GB, generous read/write limits) — effectively $0 at freemium extension scale | Medium: build a Worker that (1) receives Stripe webhooks (`checkout.session.completed`, `customer.subscription.updated/deleted`), verifies the Stripe webhook signature (use Stripe's async `constructEventAsync` + `Stripe.createSubtleCryptoProvider()` in Workers' WebCrypto environment, `node_compat = true` in `wrangler.toml`), and writes paid-status to D1/KV; (2) exposes a small read endpoint the extension polls (e.g., by email or a generated `app_id`/customer ID stored via Checkout Session metadata) to check paid status. This is the pattern documented step-by-step by Kyle Nazario (Cloudflare Workers + D1) and matches what commercial kits like "SmolStack" (~$49 boilerplate) do for server-side/edge license validation instead of insecure client-only checks. ([kylenazario.com](https://kylenazario.com/blog/paid-extension-setup-with-cloudflare), [Cloudflare Stripe webhook signature guide](https://jross.me/verifying-stripe-webhook-signatures-cloudflare-workers/)) | Fine under MV3: the extension only ever calls a documented, versioned HTTPS API you control (fetch to your own Worker URL) and gets back a JSON status flag — it does not fetch and *execute* remote code/strings, so this doesn't trip the "no remotely hosted/executed code" rule. Must still disclose in the Chrome Web Store listing that the extension is a paid/freemium product with external payment, per CWS policy, and (2026 update, enforced since Aug 1 2026) must disclose any data collected/transmitted (e.g., email sent to your Worker) in the privacy/data-disclosure section. |
| **(b) Stripe-generated license keys** | Stripe does **not** natively generate/manage license keys — confirmed via search: "Stripe does not provide tools for generating, managing, or validating software licenses." You'd need a third-party licensing service layered on top (e.g., **Keygen.sh**, **Keyforge**, **KeyStor**, **NetLicensing**) that listens to Stripe webhooks and issues a signed license key the extension can verify **offline** (no server call needed at runtime, only at activation) | Keygen has a free tier for small usage; Keyforge/KeyStor are lightweight boutique services (check current pricing, roughly $0-30/mo range for hobby volume); NetLicensing is more enterprise | Medium-low: no server code to write yourself (webhooks + key issuance handled by the third-party), but still need an account with the licensing vendor, wiring of Stripe webhooks to it, and code in the extension to validate a signed key (e.g., verify a JWT/signature client-side) — cryptographic offline verification means the extension can check paid status even without hitting any server post-activation, which is the cheapest/most resilient of these options at runtime, at the cost of relying on a third-party vendor and typically an "activation" step | Same as (a): no remote code execution, just data (a signed key) — compliant with MV3. Still must disclose paid nature + any personal data (email) sent to the licensing vendor. |
| **(c) Poll Stripe directly from the extension with a restricted/publishable key** | Stripe only | $0 infra cost | Low effort but **not recommended**: exposing enough of a Stripe key/logic client-side to check payment status invites trivial spoofing, and Stripe's restricted keys still shouldn't be embedded in publicly-readable extension code (extension source is always inspectable) | Not a real remote-code issue, but a **security anti-pattern** — since anyone can read extension source and forge "paid" state locally regardless of implementation (all these client-side authors, including ExtensionPay itself, note "there's no way to make a completely secure payment verification system since browser extension source is open"), doing this without any external check offers the weakest protection of all options — mainly relevant if piracy resistance doesn't matter much for a freemium product. |
| **(d) Third-party MoR checkout as a service (Lemon Squeezy, Paddle, Gumroad, etc.)** | Account with the MoR provider (may or may not require separately linking Stripe — Lemon Squeezy itself was acquired by Stripe in 2024 and now underlies part of Managed Payments) | Provider's blended fee (Paddle ~5%, LemonSqueezy similar, Gumroad ~10%) | Low — most of these have built-in license-key APIs and hosted checkout, closest to a true off-the-shelf MoR + licensing combo | Same MV3/disclosure notes apply; these are separate MoR providers, not "Stripe Managed Payments," so if the owner specifically wants Stripe Managed Payments this doesn't satisfy that requirement, but is worth flagging as an alternative if ExtensionPay/Connect turns out incompatible and a simpler off-the-shelf MoR is preferred over DIY. |

General MV3/Chrome Web Store notes applicable to all options: Manifest V3 bans loading and *executing* remotely-hosted code/strings (`eval`, remote `<script src>`, dynamically fetched-and-interpreted logic) — but fetching **data** from your own API (e.g., "is this user paid: true/false") and branching on it in bundled code is explicitly allowed, since all program logic ships inside the package. Since August 1, 2026, Chrome Web Store enforcement also requires prominent disclosure of **all** data collection (not just data "closely related" to the extension's single purpose) — so any email/identifier sent to a Worker, license service, or ExtensionPay must be disclosed in the listing's privacy/data-use section. Separately, paid extensions must clearly disclose that they require payment and, if applicable, that a third party (Stripe/ExtensionPay/etc.) handles billing. ([developer.chrome.com/docs/webstore/troubleshooting](https://developer.chrome.com/docs/webstore/troubleshooting), [developer.chrome.com/docs/webstore/program-policies/mv3-requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements))

## 4. Recommended concrete architecture

Given the constraints (Stripe Managed Payments desired for MoR/VAT handling, no always-on server, GitHub Pages only for docs), the cleanest path is a **direct Stripe integration** (no Connect, no ExtensionPay) plus a **free edge function** for status checks/webhooks:

**Stripe-side setup (direct account, not Connect):**
1. **Stripe account** (already created) — verify it is a plain/direct account, not enrolled as an ExtensionPay/BillingExtensions Connect-connected account, since Managed Payments excludes platform-controlled accounts.
2. **Enable Managed Payments** on the account (Dashboard toggle, subject to Stripe's eligibility review of business type/geography).
3. **Product**: create a Stripe `Product` (e.g., "Extension Pro") with `tax_code` set to the best-fit eligible code — most likely `txcd_10103000` (SaaS, personal use) if premium features are backend/API-driven and subscription-billed, `txcd_10105001` (AIaaS personal use) if the premium feature is specifically an AI capability, or `txcd_10202000/10202001` (downloadable software, personal use) if better modeled as one-time software rather than a subscribed service. Set this via Dashboard or `stripe products create --tax-code=txcd_...` / API `tax_code` param.
4. **Price**: create one or more Stripe `Price` objects on that Product (recurring for subscription, or one-time), e.g. `stripe prices create --product=prod_xxx --unit-amount=499 --currency=usd --recurring[interval]=month`.
5. **Checkout Session or Payment Link** with Managed Payments enabled:
   - Simplest no-code path: create a **Payment Link** in the Dashboard, selecting the eligible product and toggling "Enable Managed Payments" — gives a hosted URL the extension can `chrome.tabs.create` to open (`extpay`-style "open payment page" button), no server needed for checkout itself.
   - Programmatic path (if you want per-user metadata like an extension-generated customer ID): `stripe.checkout.sessions.create({ mode: 'subscription'|'payment', line_items: [{ price: 'price_xxx', quantity: 1 }], managed_payments: { enabled: true }, success_url: 'https://<your-worker>.workers.dev/success?session_id={CHECKOUT_SESSION_ID}', customer_email: <if known>, metadata: { ext_user_id: <a UUID generated client-side and stored in chrome.storage.local> } })` — requires a recent API version (`2026-02-25.preview` or later per current docs) and this call must happen server-side (i.e., in the edge function) since it needs your **restricted secret key**, never the extension itself.
6. **Webhook**: point a Stripe webhook (events: `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`) at the edge function's webhook endpoint to update a small KV/D1 record of `{ ext_user_id or email: paid_status }`.

**No-always-on-server layer:**
7. **Cloudflare account** (Workers + D1, free tier) — one Worker with two routes: `/create-checkout-session` (calls Stripe API with the restricted secret key stored as a Cloudflare secret, returns the Checkout URL) and `/webhook` (verifies Stripe signature, updates D1) and `/status?ext_user_id=...` (extension polls this on startup/periodically to read `paid: true/false` from D1).
8. **Extension side**: generate a random `ext_user_id` on install (`chrome.storage.local`), send it to `/create-checkout-session` when the user clicks "Upgrade," open the returned Checkout/Payment Link URL in a new tab, and poll `/status?ext_user_id=...` (e.g., on extension startup and every N hours) to gate premium features — this mirrors the ExtPay.js `getUser()`/`openPaymentPage()` pattern but talking to your own Worker instead of ExtensionPay's servers.

**Minimal account list for the owner:**
- Stripe account (already exists) — direct/non-Connect, Managed Payments enabled.
- Cloudflare account (free) for Workers + D1 — holds the Stripe restricted/secret API key as a Worker secret (never embedded in the extension).
- Chrome Web Store developer account (existing/required regardless, one-time $5 fee) — listing must disclose paid nature and data collected (email/user id sent to the Worker).
- Optional: GitHub Pages for docs/support page only (not for hosting the actual checkout/shop logic — consistent with the stated constraint).

This avoids ExtensionPay's ~5% surcharge and its likely incompatibility with Managed Payments, avoids any third-party licensing vendor account, and keeps 100% of the "server" on Cloudflare's free tier — the only paid recurring cost is Stripe's Managed Payments fee (3.5% + standard processing) on actual sales.
